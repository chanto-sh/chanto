# Chanto: agent notes

## Commands
- Build: `cargo build` (release: `cargo build --release`, binary at `target/release/chanto`)
- Test: `cargo test` (single test: `cargo test <name>`); agent-loop tests use a mock OpenAI server in `src/agent/tests.rs`
- Format: `cargo fmt --all` (CI runs `cargo fmt --all --check`); enable the hooks (pre-commit checks, commit-msg format) once with `git config core.hooksPath .githooks`, and don't bypass them with `--no-verify`
- Lint: `cargo clippy --workspace --all-targets` must stay warning-free (CI runs it with `-D warnings` on Linux and Windows). Code under `cfg(windows)`, or used only by Unix-gated tests, is only linted on Windows; check it from macOS or Linux with the MinGW toolchain (`brew install mingw-w64` or `apt install mingw-w64`, then `rustup target add x86_64-pc-windows-gnu`): `cargo clippy --workspace --all-targets --target x86_64-pc-windows-gnu -- -D warnings`
- Real-model smoke: `tests/real-model/smoke.sh <chanto> <base-url> <model> [provider]` has Chanto fix a one-line bug and checks the result; `.github/workflows/real-model.yml` runs it on every PR on the runner's CPU (no secrets, not required checks): Qwen3.5-4B, LFM3-1.7B and Gemma 4 E4B through llama-server's OpenAI API, and Qwen3.5-4B through Ollama's native and Anthropic APIs. `hosted-model.yml` runs it nightly against free OpenRouter models, Groq and Google AI Studio's Gemma 4 when `OPENROUTER_API_KEY` / `GROQ_API_KEY` / `GEMINI_API_KEY` secrets are set.
  - Locally: `SMOKE_FLAGS=--no-think tests/real-model/smoke.sh target/debug/chanto http://localhost:11434 qwen3.5:4b ollama`
- Test gates: `python3 scripts/test_gate.py coverage` reports the changed lines tests miss (Codecov's required 80%, Linux and Windows together). A `feat` or `fix` PR changing code must touch a test or say `Tests: none (<why>)`. `.github/workflows/mutants.yml` runs `cargo mutants --in-diff` on PRs (advisory)
- Docs drift: `python3 scripts/docs_drift.py` fails when a flag, subcommand, slash command, config key or tool isn't in the docs, or the docs give a `chanto` flag the code doesn't have. Something left out on purpose goes in `scripts/docs_drift_allow.txt` with the reason
- Debug a tool without a model: `chanto --run-tool <Tool> '<json args>'`
- Inspect prompt size: `chanto --dump-prompt`; classifier check: `chanto --classify <Tool> '<json>' "<request>"`
- Fuzz: `fuzz/` is its own crate (nightly + `cargo install cargo-fuzz`); from there, `cargo +nightly fuzz run <target> corpus/<target> seeds/<target>` with target `shell_permission`, `redact`, `url_checks` or `path_checks`. CI fuzzes pull requests with ClusterFuzzLite (`.clusterfuzzlite/`). Add a minimized crash to `fuzz/seeds/<target>/` and a unit test next to the fix
- Benchmarks: a separate repository, [chanto-sh/benchmarks](https://github.com/chanto-sh/benchmarks); clone it next to this one and run `python3 run.py --agents chanto,opencode,claude` there (it uses `../chanto/target/release/chanto`)
- Performance gate: `python3 tests/perf/gate.py --head target/release/chanto [--base <older binary>] [--device]` measures one-shot startup and the 40-turn workload against the instant mock (and, on Unix, that a one-shot question starts no `git` and a read-only session no login shell), checking this platform's ceilings in `tests/perf/budgets.json` (Linux, macOS and Windows) and, with `--base`, a Mann-Whitney test against that binary; `--device` adds the same workload pinned to one core against a small-device ceiling. CI runs it on every Rust pull request against the base commit's own build, on all three platforms, with the small-device run on Linux; its own tests are `python3 -m unittest discover -s tests/perf -p 'test_*.py'`
- Exact costs: `python3 tests/perf/exact.py --head target/release/chanto [--base <older binary>]` (Linux, needs valgrind) compares instruction counts and the size of the prompt and tools, which barely vary between runs; CI runs it with the performance gate
- Responsiveness: `python3 tests/perf/responsive.py --bin target/release/chanto` checks that an idle TUI draws nothing and stays under a CPU ceiling, typing and PageUp, and shell commands' CPU and process count (Windows: shell only, since it has no pseudo-terminal here); ceilings under `responsive` in `tests/perf/budgets.json`
- Chaos: `python3 tests/chaos/invariants.py --bin target/debug/chanto [--tier pr|nightly] [--only NAME] [--seed N]` runs stream, shell, crash, environment and TUI fuzz chaos against the fake model, and fails on a panic, hang, orphan, broken session, write outside the project or leaked secret; a failure prints its seed. CI runs it (`chaos.yml`), advisory for now
- Stress: `python3 tests/perf/stress.py --bin target/release/chanto` runs a 2,000-turn session and a 30,000-file tree against the fake model (memory, slowdown, Grep against `rg -l`, and with clangd installed, no language server in a large project without a compile database); CI runs it after the performance gate on Linux and macOS, with ceilings in `tests/perf/budgets.json` under `stress`

## Releases
- Use an isolated worktree from current `origin/main`; preserve other agents' uncommitted work. Prepare a release PR and wait for every required check, including CodeQL, fuzz and visual, before merging. Do not bypass checks or force-push a published tag.
- Align `Cargo.toml`, `desktop/Cargo.toml`, `core/Cargo.toml`, their `Cargo.lock` entries, `ide/vscode/package.json` and `ide/jetbrains/build.gradle.kts`. `chanto-core` is released with chanto under the same version, and `Cargo.toml` and `web/Cargo.toml` require it exactly (`=X.Y.Z`). Keep `proto` at its existing version unless its wire types changed.
- User-visible changes add a fragment, `changelog.d/<name>.md` (one or more `- **Title.** text` items), rather than editing CHANGELOG.md, so open PRs don't conflict. In the release PR, `python3 packaging/changelog.py vX.Y.Z` moves the Unreleased entries and every fragment into `## vX.Y.Z (Month D, YYYY)`, keeps an empty **Unreleased** heading and deletes the fragments; `check-release.py` refuses leftover fragments. Update the six welcome snapshots for the displayed version. For security releases raise `min_version` in `install.sh`, `$minVersion` in `install.ps1`, and the documented floor in `docs/reference.md`.
- Before pushing, run `python3 packaging/check-release.py vX.Y.Z`, `bash tests/install.sh`, and `cargo test --locked --lib visual_snapshots -- --ignored --test-threads=1`; review any snapshot differences. Metadata validation also runs once before all release builds.
- Merging the release PR is the last manual step: `.github/workflows/tag-release.yml` sees the untagged version on main, reruns `check-release.py` and pushes an annotated `vX.Y.Z` tag on the merged commit as the release GitHub App (the only non-admin allowed to create `v*` tags), which starts `.github/workflows/release.yml`. If that run fails, re-run it rather than tagging by hand. Releases serialize without canceling an active run because they update shared latest pointers. Cut one version at a time; GitHub keeps only one pending run in this concurrency group.
- Every archive, npm package, Homebrew install and container image carries `LICENSE`, `NOTICE` and `THIRD_PARTY_LICENSES.txt` (generated by cargo-about in the release's preflight job from `about.toml` and `packaging/third-party-licenses.hbs`). A new dependency license must be allowed in both `deny.toml` and `about.toml`.
- Keep release actions pinned by SHA, Rust and `cross` pinned to tested exact versions, dependencies locked and release builds uncached. Upgrade tool pins in reviewed PRs. Hosted OS images, cross container tags and signing timestamps still vary; do not claim byte-for-byte reproducibility.
- Wait for all five archives, the `@chanto/web` package, signed checksums, provenance, Homebrew, npm (`@chanto/cli` and `@chanto/web`), crates.io and container jobs, and `sdk publish`, which the same tag starts. Verify a downloaded archive against the signed checksum file and run its `--version`. Report publication complete only after checking the package channels, including any npm staging/approval state.
- On failure, inspect the specific job and retry only what is safe. Reuse already published immutable artifacts; never overwrite a released version, move its tag, or rebuild assets behind existing checksums. The final `verify published release` job independently downloads public assets, verifies both checksum signatures and all archive provenance, smoke-tests the Linux binary, waits for public package availability and anonymous container access, compares the npm Linux package payload with the signed binary, and verifies the container signature/provenance. A new GHCR package needs its one-time visibility setting changed to Public in GitHub package settings; repository visibility alone does not do this. A successful GitHub release job alone does not prove every package channel is available.

## Security checks
- Run `scripts/scorecard-check.sh` for OSV, workflow and local Scorecard checks. Advisory exceptions must include an applicability rationale; do not lower the baseline to silence a finding.
- The block-buffer exception is version/checksum-limited by `scripts/check-advisory-exceptions.py`. Run `python3 -m unittest discover -s tests/scorecard` after changing it. Keep custom validation in a prerequisite job, not inside Scorecard's restricted publishing job.

## Architecture
- `agent/` owns the loop: `turn.rs` (`run_turn` → `call_model` → `execute_calls` → repeat), `model.rs` (one streaming call), `calls.rs` (executing calls, spend guard), `authorize.rs` (permission decisions), `compact.rs`, `session.rs` (checkpoints, rewind, forks), `verify.rs` (guardrails, oracle), `subagent.rs`, `protocol.rs` (text tool protocol, argument normalization), `background.rs`. `agent.rs` keeps the `Env` and `Agent` state and its accessors. Tests live in `agent/tests.rs`; `#[cfg(test)]` modules are separate `*_tests.rs` files.
- Frontends implement `agent::Frontend` (emit events, permission prompts, questions): `tui/` (ratatui; `draw.rs`, `keys.rs`, `mouse.rs`, `events.rs`, `pickers.rs`, `render.rs`, `stream.rs`, `run.rs`), `plain.rs` (print/REPL).
- `remote.rs` (`/remote`): `Mirror` wraps the TUI's frontend to also serve the session to the web UI over the tailnet; prompts are raced (first answer wins) and phone input reaches the TUI as `AppMsg::Remote`.
- Tools implement `tools::Tool`; `kind_for(args)` drives permission decisions in `permissions::static_decision`. Auto mode falls back to `permissions::classify`.
- `llm.rs`: `Provider` speaks Ollama `/api/chat` (NDJSON) or OpenAI `/chat/completions` (SSE); `Env::resolve` maps `provider/model` specs to named providers.
- Large modules keep a thin root `.rs` and move cohesive subsystems into a same-named directory of submodules (as `agent.rs`/`agent/` does): `guardrails.rs` + `guardrails/select.rs` (related-test selection), `hooks.rs` + `hooks/verdict.rs` (prompt/agent model-verdict hooks).

## Wire types (`proto/`)
- Test: `cargo test -p chanto-proto`. Root `cargo build`/`cargo test` skip it.
- `proto/` is wire types only, shared by the CLI and the hosted service; additive changes only, since old CLIs must keep parsing responses.

## Conventions
- Keep the system prompt prefix stable within a session (KV-cache reuse on local servers); put per-turn context in user messages as `<system-reminder>`.
- Tool output for the model goes in `ToolOutput.content`; human-facing summaries in `.display` (may contain ANSI).
- `chanto serve`'s events and request bodies are defined in `src/wire.rs`; build events from those types, not `json!`. After changing them, run `UPDATE_SCHEMA=1 cargo test --features schema --lib wire::` and `python3 sdk/gen_types.py` (CI checks `sdk/schema.json` and the SDKs' generated types are current).
- Public URLs come from `site_url!()` / `api_url!()` in `src/site.rs`.
- Commit messages follow Conventional Commits, checked by `.githooks/commit-msg` and on PR titles in CI: `<type>(<scope>): <summary>`, with type one of feat, fix, perf, refactor, docs, test, build, ci, chore, revert, style. The scope is optional, lowercase and names the area touched (`tui`, `hooks`, `sandbox`, `classifier`, `deps`). The summary is imperative, lowercase, has no trailing period, and the whole subject fits in 72 characters. The body says why. Breaking changes get `!` plus a `BREAKING CHANGE:` footer. A `feat`, `fix` or `perf` pull request adds a `changelog.d/<name>.md` fragment (CI checks), or opts out with a `Changelog: none (<why>)` line in its description. No AI attribution lines. Full rules are in CONTRIBUTING.md#commit-messages.
- Comments describe Chanto's own behaviour. Name another agent only where the code really interoperates with its files or protocol (`.claude/`, `CLAUDE_*` aliases, hook payloads).
- Keep modules to a readable size: when a `*.rs` file grows past ~2.5k lines, split a self-contained subsystem into a `module/submodule.rs` rather than letting it sprawl. A submodule starts with `use super::*;`; items the parent still calls are `pub(super)`, everything else stays private. Move a function's doc comment with it (an orphaned `///` left behind trips clippy's `empty_line_after_doc_comments`).
